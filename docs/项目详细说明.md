# 项目详细说明

> 智能家居商城 —— AI 多智能体客服 + 电商平台
> 本文是项目的**完整技术说明**：架构、状态机、数据流、可靠性、安全、部署与测试。

---

## 1. 项目定位

一个**完整的 Agent 工程**，而不是「调一次大模型返回一段话」的 Demo。
它同时具备一个 Agent 项目应当有的五件东西：

| 要素 | 在本项目中的落点 |
|------|------------------|
| **自主决策循环** | `react.py` 受限 ReAct：子 Agent 自行决定调哪个工具、要不要再调一次，有步数上限与兜底 |
| **可用记忆** | 三层：checkpoint 热记忆（多轮图状态）+ PostgreSQL 耐久记忆（会话消息）+ 澄清 `pending_intent`（跨轮意图） |
| **韧性** | 路由失败降级、工具异常隔离、Redis 熔断降级、LLM 未配置走友好话术而非 500 |
| **可观测性** | `agent_traces` 表 + `/api/traces` + LLM 用量计量 + 结构化日志 + `/api/health` |
| **安全** | JWT 鉴权 + IDOR 防护 + 服务端注入鉴权主体 + prompt 与用户输入隔离 + Internal Token |

业务上覆盖两条线：

- **AI 客服线**：FAQ 知识库检索（ChromaDB RAG）、订单/物流/售后/购物车查询、订单列表、自然语言下单；
- **电商线**：注册登录（JWT + bcrypt）、商品浏览、购物车、下单（防超卖）、支付（幂等）、物流、售后 —— 完整交易闭环。

## 2. 技术栈

| 层 | 选型 | 说明 |
|----|------|------|
| Web 框架 | FastAPI + uvicorn | SSE 流式原生支持 |
| 编排 | **LangGraph**（Supervisor 单图 + 受限 ReAct 子 Agent） | 未用 `create_react_agent` 子图，理由见 §5 |
| LLM 接入 | 自研 `LangChainChatModel`（BaseChatModel 适配器）→ OpenAI 兼容端点 | 默认 DeepSeek Chat |
| 向量库 | ChromaDB + sentence-transformers（`paraphrase-multilingual-MiniLM-L12-v2`） | 本地持久化，支持混合检索（向量 + BM25） |
| 数据库 | PostgreSQL 15（psycopg2 连接池 + SQLAlchemy） | `shop.*` 电商表 + `customer_service.*` 会话表 + `agent_traces` 轨迹表 |
| 缓存 | Redis 7（Cache-Aside，**可选**） | 不可用自动熔断降级 |
| 图持久化 | `AsyncSqliteSaver`（langgraph-checkpoint-sqlite 3.x） | 落 `checkpoints.db` |
| 鉴权 | PyJWT（HS256）+ bcrypt | — |
| 前端 | 单文件 `static/index.html`（原生 JS + SSE） | 逐字打字机渲染 |

### 本机运行环境（便携式 Python）

```
解释器      D:\python.exe（Python 3.13.7）
依赖        D:\Lib\site-packages      ← 不在 sys.path 上，必须 PYTHONPATH 指定
pip 入口    pip.bat                   ← 等价 set PYTHONPATH=D:/Lib/site-packages && python -m pip
```

> **为什么需要 `pip.bat`**：便携式布局下 `site-packages` 不在 `sys.path`，
> 而 pip 自身就装在 `site-packages` 里 —— 所以 `D:\python.exe -m pip` 会报
> `No module named pip`。`pip.bat` 只是把 `PYTHONPATH` 设好再调 `python -m pip`。
> 运行应用同理需要 `PYTHONPATH`（见 `run.bat`）。

## 5. 多智能体图（核心）

### 5.1 为什么不用 `langgraph.prebuilt.create_react_agent` 做子图

1. 子图会继承父图 checkpointer，state 命名空间要额外处理；本项目的子 Agent 只是
   「一次请求内的短循环」，**不需要独立持久化**；
2. 本项目工具是自定义 `Tool` 包装（非 LangChain 原生 tool），需要一个能被离线
   脚本模型**确定性驱动**的循环，便于回归测试；
3. 需要精确控制「哪次 LLM 调用是工具决策、哪次是最终回答」，从而让 token 只流
   用户可见的正文。

### 5.2 状态 `MasterState`

| 字段 | 类型 | 用途 |
|------|------|------|
| `messages` | `Annotated[list, add_messages]` | 对话消息（checkpoint 持久化，多轮累积） |
| `route` | `str` | 归一化后的**白名单**路由 |
| `extract` | `str` | 主要参数摘要（订单号等），用于展示与 trace |
| `slots` | `dict` | 槽位：`order_id` / `ticket_id` / `product` / `address` / `quantity` / `recipient` |
| `user_query` | `str` | 本轮用户原话（避免从 messages 反推） |
| `user_id` | `str` | **鉴权主体**，数据隔离与服务端注入的依据 |
| `pending_intent` | `dict \| None` | 反问后待续跑的意图（澄清闭环） |
| `pending_order` | `dict \| None` | 待确认的订单草稿（下单两阶段） |
| `order_action` | `str \| None` | `prepare` / `commit` / `cancel` |
| `order_mode` | `str` | `single`（点名单品）/ `cart`（购物车整单），见 §5.6.1 |
| `tool_steps` | `Annotated[list, _append_steps]` | 工具调用轨迹（累积，最多 60 条） |

### 5.3 节点清单（共 13 个）

| 节点 | 类型 | 职责 |
|------|------|------|
| `supervisor` | LLM | **只做分类 + 抽槽 + 指代消解**（带最近几轮历史；省略句 + `last_order_id` 确定性恢复），不产出面向用户的回答 |
| `faq_agent` | ReAct | 知识库混合检索 |
| `order_agent` | ReAct | 单订单查询 / 我的订单列表 |
| `logistics_agent` | ReAct | 物流轨迹（含读取时状态推演，见 §5.5） |
| `after_sale_agent` | ReAct | 售后工单进度 |
| `cart_query_agent` | ReAct | 购物车内容 |
| `list_orders_agent` | ReAct | 订单列表 |
| `product_agent` | ReAct | 在售商品浏览（`list_products` 列全部 / `search_products` 按词检索） |
| `place_order_prepare` | 确定性 | 只读校验商品/库存 + 生成草稿回显（**不写库**）；单品按关键词检索，整单读购物车（§5.6.1） |
| `place_order_commit` | 确定性 | 用户确认后单事务落库：单品 `create_direct` / 整单 `OrderService.create` |
| `place_order_cancel` | 确定性 | 丢弃草稿 |
| `clarify` | 确定性 | 缺参反问 + 写入 `pending_intent` |
| `finish` | LLM（流式） | 闲聊兜底，直接 `astream` 产出 token |

**图结构**：`supervisor` 是唯一入口，条件边 `create_selector` 依据纯函数
`resolve_target()` 选目标；**所有节点都连到 `END`**（单轮一次路由，不做多跳）。
`create_selector` 会把非法目标降级为 `finish` 并打 warning —— 因此**条件边永不 `KeyError`**。

> 为什么路由只跳一次：客服场景的意图几乎不会在一轮内连续切换；
> 强制单跳能让状态机可预测、可单测，也避免「路由震荡」把对话绕晕。

**工具绑定策略（软引导，不切碎）**：查询类子 Agent **共用同一套只读工具**
（`master_graph.READ_TOOLS`），领域差异由各域 prompt 做「软引导」（优先用哪把、
什么时候换一把、拿到不完整结果要自己补全），而不是按 route 把工具切碎后硬绑。
理由：工具宇宙若在 LLM 看到之前就被 route 切死，子 Agent 只能「盒内自治」，
无法编排多步。**安全性不靠切工具**，而靠 ①只读工具无副作用 ②写操作走确定性
两阶段 ③身份由服务端注入 —— 放开只读工具集不动这三条边界。

> 反例（曾经的坑）：`list_orders` 只挂 `list_my_orders`，用户问「哪笔订单没付款、
> 我买了什么」时，子 Agent 拿到订单列表后手边没有第二把工具取商品明细，只能回
> 「接口没返回明细」把问题抛回用户。现由 `tests/test_agent_offline.py` T19 守这条
> 回归（断言单轮内依次调用 `list_my_orders` → `query_order`，且第二个工具拿到明细）。

**商品浏览能力**：`list_products` 是只读工具，**无需关键词**即可列出在售商品。
与 `search_products` 的分工：后者 `keyword` 必填、空词返回 `[]`（服务的是下单前
核对商品/库存，防止空词误列全库）；前者专服务「有什么商品在售」这类浏览诉求。
路由白名单新增 `product` → `product_agent`，避免该问题被兜底成 `finish`（无工具）
而答不出。回归由 T20 守（断言 `route == "product"` 且真的调用了 `list_products`）。

**商品名的模糊匹配**：用户极少一字不差地报商品全名（实录：说「X1 门锁」，库里是
「X1 智能门锁」）。`tools/order_search.search_products` 因此分三层逐层放宽 ——
① SQL 侧「任一 token 命中」粗筛 → ② 分词 AND → ③ Python 侧**字符覆盖率**精排；
排序键 `(覆盖率, 长度比)` 降序、同分按 id 升序。核心排序是纯函数
`match_products(keyword, rows)`，可离线断言（T22）；真实库集成由 T24 守
（断言「X1 门锁」命中「X1 智能门锁」，且 off_sale 的配件包不出现）。
覆盖率阈值 `PRODUCT_MATCH_COVERAGE_MIN`（默认 0.6）。

**跨轮指代消解**：用户第二句常是省略句（「那笔订单」「当前状态」「到哪了」）。旧版
supervisor 只把**本轮原话**喂给 LLM、订单号也不跨轮保留 → 子 Agent 手边没有单号，
只能反问「请把订单号发给我」（实录）。现在 ① supervisor 判意图时带上最近几轮历史
（`SUPERVISOR_HISTORY_WINDOW`）；② 最近订单号持久化在 `state.last_order_id`（下单
commit 即刻回写，同时写回 `slots.order_id`）；③ 本轮 route 掉到 `finish`、但话里含
意图提示词时，用 `promote_status_query` + `recent_order_id` 做**确定性提升**与单号
补全（只认「订单号：xxxx / #xxxx」这类**带前缀**编号，不认裸数字）。没有上下文时
不提升。回归由 T23 守（纯函数 + supervisor 节点两层），端到端由场景 4B 守。

**物流状态的读取时推演**：虚拟支付只写入一条「已揽件」记录，此后**没有任何后台
任务推进它** —— 新订单物流会永远停在揽件态。`domain/shop/logistics/service.py` 的
`derive_logistics` 在**读取时**按距揽件的经过时间补出
`已揽件 → 运输中 → 到达派送点 → 派送中 → 已签收`：**纯计算、不回写数据库**，只对
自动生成的初始态（`status == 'picked_up'` 且轨迹 ≤1 条）生效，`init.sql` 种子数据
的完整轨迹原样返回。阈值默认 0/2/5/8/12 分钟（演示尺度），可用环境变量
`LOGISTICS_STAGE_MINUTES` 覆盖。回归由 T21 守（纯函数 + 服务集成两层）。

### 5.4 一次请求的完整生命周期

```
POST /api/chat/stream  {conversation_id, message}
  │
  ├─ 1. JWT → user_id；_assert_conversation_owner(conv, user_id)   ← IDOR 防护
  ├─ 2. agent.run_stream(...)
  │     ├─ per-conversation asyncio.Lock  ← 同会话串行化
  │     ├─ _prepare()：
  │     │     ├─ checkpointer 取图状态（热记忆）
  │     │     ├─ 拿不到 → 用 PostgreSQL 历史回填（耐久记忆）
  │     │     └─ add_message(user)  ← 锁内写入
  │     ├─ graph.astream(stream_mode=["updates","messages","custom"])
  │     │     ├─ supervisor：LLM 抽 route/slots → 合并跨轮槽位 →
  │     │     │             恢复 pending_intent → 正则兜底补单号 → 判 order_action
  │     │     ├─ resolve_target() → 目标节点
  │     │     ├─ 子 Agent：ReAct（工具经 asyncio.to_thread 执行，注入 user_id）
  │     │     ├─ messages 模式 → 逐 token yield {"event":"token"}   ← 打字机
  │     │     ├─ custom 模式 → {"event":"tool", status: start/done}
  │     │     └─ updates 模式 → routing / 节点进度 / agent_result
  │     └─ 收尾（仍在锁内）：TraceRecorder.save(usage) +
  │                          add_message(assistant)
  └─ 3. SSE 结束事件：{"event":"done", route, usage, conversation_id}
```

### 5.5 澄清闭环状态机

```
用户："帮我查订单"
  → supervisor: route=order, slots={}            （LLM）
  → resolve_target: order 缺 order_id → "clarify"
  → clarify: "请把订单号发给我～（纯数字，例如 1001）"
             pending_intent = {route: order, slots: {}, missing: [order_id]}

用户："1001"
  → supervisor: LLM 判成 finish（很正常）
  → ② 恢复 pending：route 覆盖回 order
  → ④ 正则兜底：extract_order_id("1001") = "1001" → slots.order_id
  → resolve_target: order 槽位齐全 → "order_agent"
  → 返回真实订单详情
```

> **关键顺序**：正则补参必须在「恢复 pending」**之后**、且按**最终** route 判断。
> 否则用户只回 `"1001"` 时 LLM 判 `finish`，永远走不到补参分支（这是曾经的 bug，有回归测试守着）。

必填槽位表（`routing.py`）：

| route | 必填槽位 | 反问话术来源 |
|-------|----------|--------------|
| `order` | `order_id` | `ORDER_ID.question` |
| `logistics` | `order_id` | 同上 |
| `after_sale` | `order_id` 或 `ticket_id` | `AFTER_SALE_REF.question` |
| `place_order` | `product`、`address` | 两槽位分别反问 |

### 5.6 下单两阶段状态机（human-in-the-loop）

```
用户："我要买智能门锁1个，寄到广州市天河区体育西路1号"
  → supervisor: route=place_order, slots={product:智能门锁, address:...}
  → order_action=prepare（无 pending_order）
  → resolve_target: 槽位齐全 → place_order_prepare
  → prepare：确定性检索商品（不经 LLM）→ 校验库存 → 生成草稿
              pending_order = {product_id, name, price, quantity, address,
                              recipient, total, stock}
  ← 回显："下单成功请确认：X1 智能门锁 ×1 / ¥1599.00 / 地址：…"

用户："确认"
  → supervisor: pending_order 存在 + is_affirmative("确认") → order_action=commit
  → resolve_target → place_order_commit
  → commit：OrderService.create_direct() 单事务落库

用户："不要了"
  → is_negative → order_action=cancel → place_order_cancel → 丢弃草稿
```

**三个设计要点**：

1. **金额/库存不经 LLM**：`prepare` 用确定性检索拿真实价格与库存，避免 LLM 编造；
2. **否定优先**：`is_affirmative` 先排除否定词 —— 中文「不要」包含「要」、「不是」包含「是」，
   只做包含匹配会误判（这是曾经的 bug）；
3. **话题漂移即丢弃草稿**：`pending_order` 存在但用户聊别的 → 丢弃，避免挂着一个过期确认。

### 5.6.1 两种下单模式：单品直购 vs 购物车整单

`order_mode` 由纯函数 `routing.resolve_order_mode()` 判定，**只看本轮 LLM 抽到的 `product`
槽位**（上一轮遗留的不算 —— 否则「先问 X1 门锁多少钱」再「帮我下单」会被误判成买那一件）：

| 模式 | 触发 | 商品来源 | 落库 | 必填槽位 |
|------|------|----------|------|----------|
| `single` | 点名了商品 | `search_products` 模糊匹配 | `create_direct`（不碰购物车） | product + address |
| `cart` | 没点名商品 | 用户购物车里的全部商品 | `OrderService.create`（锁行 → 建单 → 清空购物车） | address |

```
用户（购物车已有 2 件）："帮我结算购物车，寄到广州市天河区"
  → supervisor: route=place_order, slots={address}（无 product）→ order_mode=cart
  → resolve_target: cart 模式只要求地址 → place_order_prepare
  → prepare(_prepare_cart)：读购物车 → 逐件校验在售/库存 → 多商品草稿
  ← 回显："请确认结算购物车中的以下商品：· A … · B … 合计 ¥4098.00"

用户："确认"
  → commit：**先比对**购物车是否仍是草稿那一份（防确认后被改动）
           → OrderService.create() 单事务落库 → 清空购物车
```

旧版没有 `cart` 模式：购物车里放了多件却说「帮我下单」时，prepare 拿空关键词去检索，
只能回一句「没有找到与「」匹配的商品」，或按 LLM 猜到的某一件只下 1 件、其余静默忽略。

回归由 T27 守（纯函数 + supervisor 节点 + 图级整单）；端到端由 `scripts/e2e_mock.py`
场景 4C 守（加购 2 件 → 整单 → 断言订单含全部 2 件、购物车被清空）。

> 注意：图的三个下单节点以 `search_products` 是否在场为装配开关。`cart` 模式并不用它，
> 但裁剪只读工具集时若删掉 `search_products`，整单结算会一起被关掉。

`tools/base.py` 的 `Tool` 是薄包装：`run(params)` 做参数校验 → 调底层函数 → 返回字符串。

|------|--------------------|------|

### FAQ 多路召回（`search_multi`，关键词堆兜底）

`search_faq` 不走单路 `RAGStore.search`，而是 `RAGStore.search_multi`。原因是 RAG 检索对
**「空格分隔的关键词堆」**语义表达很差：LLM 会把「它的电池能续航多久」写成
`X1 智能门锁 电池 续航`，主体词占满语义权重、诉求被稀释 → 首位命中「X1 可以同时被几台手机
控制？」；正确答案「电池能用多久？」掉到第三，再被 `_dedup_by_source`（每商品保留 1 条）挤掉，
最终只能答「没有相关资料」（UI 实录）。

实现要点（`infrastructure/rag/retriever.py`）：

| 环节 | 说明 |
|------|------|
| `generate_query_variants` | 纯函数。原句 + （分段 ≥3 时）尾部两段 / 尾段 / 去空白紧凑版 + （含标点时）各分句；过滤空、重复、长度 <2、纯疑问虚词（「怎么办？」）；最多 5 个 |
| `_candidates` | 从原 `_search_impl` 抽出的**去重前**候选池（向量 + BM25 + 重排 + 关键词加成），逻辑未变 |
| `_search_impl` | = `_dedup_by_source(self._candidates(...))` —— 单路行为完全不变 |
| `fuse_results` | 纯函数。各变体**按自身最高分归一后求和 ÷ 变体数**（共识优先，分数落回 `[0,1]`），最后按来源去重 |
| `search_multi` | Cache-Aside。**变体数 ≤1 时直接委托 `search`**（自然问句零额外开销、复用既有缓存）；否则各变体取候选池 → 融合 → 整体缓存（键带 `"multi"` 前缀） |

**为什么融合必须在去重之前**：`_dedup_by_source` 会保证「每来源 1 条」，而同一商品的多条 FAQ
同属一个来源 —— 若先走单路（含去重）再融合，正确答案在参与排序前就被丢掉了。

回归由 `tests/test_agent_offline.py` T25（纯函数：变体派生 + 共识融合）/ T26（真实 FAQ 库）守，
端到端由 `scripts/e2e_mock.py` 场景 3E 守（Mock LLM **故意**把问句压成关键词堆，断言回答里出现
只有正确条目才有的「6 个月」）。实测真实语料命中 11/16 → 13/16。

### 鉴权主体注入（重要安全机制）

工具声明了 `user_id` 参数，但**不由 LLM 填写**。`react.py` 的 `_inject_context()` 在调用前注入：

```python
declared = {p.name for p in tool.parameters if p.name in context}  # 只注入声明的参数名
return {**args, **{k: context[k] for k in declared}}               # 服务端值覆盖 LLM 值
```

- **安全**：鉴权主体永远来自 JWT（`state["user_id"]`），LLM 无法伪造越权身份；
- **兼容**：不会把 `user_id` 硬塞给 `search_faq` 这类不声明它的工具，避免参数校验失败。

> 这个机制之前是缺失的：ReAct 只透传 LLM 给的 args，导致所有订单/物流/售后工具
> 一律返回「请先登录」。因为下单节点自己解析了 uid（绕过工具层），离线测试没能发现 ——
> 是端到端 Mock LLM 验证才暴露。现已补测试 T14 守住。

**身份解析必须是精确匹配**（`tools/order_search._resolve_user_id`）：
只接受数字 id，或与 `email` / `nickname` **完全相等**的值。
旧版用 `email ILIKE '<user_id>%'` 做前缀匹配，等于「谁先命中谁就是你」，
`sub="a"` 能匹配到任意 a 开头的邮箱 —— 属身份混淆，已修并加测试 T17 守住。

### 工具调用的超时与线程纪律

工具是**同步函数**（内部有 DB / 向量检索 I/O），统一在 `react._call_tool` 里执行：

```python
obs = await asyncio.wait_for(
    asyncio.to_thread(tool.run, call_args), timeout=TOOL_TIMEOUT_SEC)  # 默认 8s
```

- **必须走线程池**：同步工具直接在事件循环里跑会阻塞整个进程；
- **必须有超时**：否则一次卡住的 DB 查询会永久占用一个工作线程，工具层逐渐饿死；
  注意 `to_thread` 的线程**无法被真正取消**，`wait_for` 只是让调用方快速失败，
  所以必须与连接池的 `statement_timeout` **双保险**；
- 超时/异常都返回**可读降级文案**，不中断整个请求。

### `place_order` 工具为什么不在图里

Master 的下单走**确定性两阶段**（金额/库存/收件人不经 LLM）。这个工具是给
「非图路径」（脚本、将来的其它前端）留的直接调用入口，若塞回图里会与两阶段语义重叠。
`main.py` 只注册图真正会绑定的 **8 把只读工具**（`place_order` 不在其内）。

> 另注：`tools/order_search.py` 里原本还有一个**无鉴权**的「列出全站订单」函数
> 并被 re-export，已删除 —— 它一旦被误注册成 Agent 工具就是「一句话导出全站订单」。
> 真正的管理员列表在 `apps/shop/b_endpoint/admin.py`，带 `Depends(require_admin)`。

## 7. LLM 适配层与流式

```
ChatService (llm/client.py)                    openai SDK
  ├─ call_raw(messages, tools)        ← 非流式，返回完整响应（含 tool_calls）
  └─ stream_raw(messages, tools)      ← 真流式，逐 delta yield
                                          {"content", "tool_calls":[{index,id,name,arguments}]}

LangChainChatModel (llm/langchain_model.py)    BaseChatModel 适配器
  ├─ _generate(messages, stop, run_manager, **kw)  ← 非流式（supervisor 路由 / 兜底）
  ├─ _stream(...)                                  ← 逐 delta yield ChatGenerationChunk(AIMessageChunk)
  └─ bind_tools(tools) → 新实例（_bound_tools 用 PrivateAttr 声明）
```

三个必须写进注释的坑：

1. **`_generate` 必须显式声明 `run_manager`**：langchain-core 的 `_agenerate` 默认实现会把它
   **作为位置参数**传入；少声明就是
   `TypeError: _generate() takes from 2 to 3 positional arguments but 4 were given`。
   这个错误只在真实调用链上出现（脚本模型自己声明了该参数，测不出来）→ 已加 T16 守住。
2. **`tool_call_chunks` 必须原样透传并按 index 拼接**：流式响应里 `arguments` 是**片段**，
   丢片段会导致带工具的流式响应丢失 `tool_calls`，ReAct 会误判「不需要工具」直接返回空回答。
3. **`_bound_tools` 用 pydantic `PrivateAttr`**：旧版用 `setattr` 挂私有属性，在 pydantic v2 下
   属于未声明字段，行为依赖模型配置。

### SSE 事件协议

| `event` | 关键字段 | 前端行为 |
|---------|----------|----------|
| `supervisor` | `status=executing` | 显示「正在分析意图...」 |
| `routing` | `status=routed`, `route`, `extract` | 显示「已路由到: 订单查询」 |
| `tool` | `name`, `status`(start/done), `duration_ms` | 显示「调用工具 query_logistics...」 |
| `token` | `node`, `content`（1 段文本增量） | **逐字追加**（打字机） |
| `agent_result` | `content`, `route` | 未流式过的节点兜底渲染（与 token 去重） |
| `done` | `route`, `usage`, `conversation_id` | 收尾、补标签 |
| `error` | `message` | 提示错误 |

> 实现注意：`stream_mode="messages"` 会**既**吐流式增量（`AIMessageChunk`），
> **又**吐节点 return 的整条消息（`AIMessage`）。只转发 `AIMessageChunk`，
> 否则前端会收到 2 倍内容（逐字 + 整条重发）。已加 T15 守住。

## 8. 记忆与持久化

三层记忆，各司其职：

| 层 | 载体 | 内容 | 生命周期 |
|----|------|------|----------|
| **热记忆** | `checkpoints.db`（`AsyncSqliteSaver`） | 图状态（messages / slots / route / pending） | 进程重启仍在 |
| **耐久记忆** | PostgreSQL `customer_service.messages` | 逐条问答（带 `turn_number`） | 永久 |
| **跨轮意图** | state 内 `pending_intent` / `pending_order` | 反问后待续跑意图、待确认订单草稿 | 下一轮消费 |

**记忆补齐**：`MasterAgent._prepare()` 若在 checkpoint 查不到该会话（首次 / 换库 / 被清理），
用 PostgreSQL 历史回填 —— 避免「重启后多轮上下文凭空消失」。

**为什么必须统一异步**：`AsyncSqliteSaver.__init__` 内部调用 `asyncio.get_running_loop()`，
只能在运行中的事件循环内构造。旧版在 import 期构造 → 抛 `RuntimeError` → 被 `except` 吞掉 →
静默退化成内存态（`checkpoints.db` 有表但 0 行，持久化从未生效）。现在只在 FastAPI lifespan 里创建。

**消息表**：`turn_number` 由 `KeyedLocks` 保护下计算，保证「用户消息 + 助手消息」成对且序号唯一。

## 9. 并发模型

| 场景 | 手段 |
|------|------|
| 同会话并发请求 | `MasterAgent` per-conversation `asyncio.Lock` —— 串行化整轮处理（图状态按 thread_id 存，并发写会互相覆盖） |
| 「用户消息 + 助手消息」成对写入 | 锁范围**覆盖成对写入**（只锁单条 INSERT 不够，成对才能保证问答不错配） |
| `turn_number` 竞态 | `utils.KeyedLocks`（按 conversation_id 互斥），锁内计算 turn_number |
| 同步工具/DB 阻塞事件循环 | **所有**同步 I/O 一律 `asyncio.to_thread`：工具调用 + 会话管理（`create/get_context/add_message`）+ trace 落库。**新增代码若在 async 路径里直接调同步函数，就是 bug** |
| 工具执行失控 | `asyncio.wait_for(..., TOOL_TIMEOUT_SEC)` 对外超时（默认 8s），配合连接池 `statement_timeout` 双保险 |
| 购物车重复结算 | `OrderService.create` 先 `SELECT ... FROM shop.cart_items ... FOR UPDATE OF ci` 锁购物车行，后到者读到空集 |
| 库存超卖 | `SELECT ... FOR UPDATE` + `UPDATE ... WHERE stock >= qty` 双保险 |
| 支付/取消幂等 | `FOR UPDATE` + 状态检查 |
| 连接池初始化 | `ThreadedConnectionPool` 双检加锁（避免并发创建多个池）；池上限**故意**小于线程池上限，让池耗尽成为背压 |
| 后台任务 | `asyncio.create_task` 跑超时订单扫描（单进程 demo 够用；多副本应换分布式调度） |

**三层锁的作用域与边界**（进程内锁只在单副本有效，多副本需换 DB 行锁 / Redis 锁）：

| 锁 | 作用域 | 解决的问题 |
|----|--------|------------|
| `MasterAgent._locks`（asyncio.Lock） | 单进程 | 同会话并发写 checkpoint 互相覆盖 |
| `ConversationManager._locks`（KeyedLocks） | 单进程 | `SELECT max(turn_number)` 与 `INSERT` 的竞态 |
| PostgreSQL 行锁（`FOR UPDATE`） | 跨进程 | 库存、购物车、订单状态 |

**证据**：
- T11 —— 5 个并发请求 → 消息总数恰为 10，`user.turn_number` 唯一且为 `1..5`，问答正确配对；
- T18 —— 同一用户并发结算：恰好一单成功、另一单因购物车已空失败、库存只扣一次；
- `_scratch/probe_loop_block.py` —— A/B 实测事件循环滞后 `14.9ms`（走 to_thread）vs `428.3ms`（直接阻塞）。

> 排查提示：把同步路由误改成调用 async 函数而**忘写 `await`**，不会抛异常 ——
> 协程被创建但从不执行，效果是「该校验静默失效」。端到端场景 6 抓到过一次。

## 10. 可靠性：缓存与降级

### Redis Cache-Aside

```
读路径： cache.get(key) ──命中──→ 返回
                        └─未命中─→ 查源（DB / RAG）→ cache.set(key, ttl)

命名空间  rag:faq:*   FAQ 混合检索结果，key = hash(query, top_k, product)，TTL 600s
          rag:shop:*  商品详情 / 列表 / 分类树，TTL 300~600s

失效      知识库 re-ingest        → invalidate("faq")
          下单 / 取消（库存变化）  → invalidate("shop")
```

**为什么缓存这两处**：FAQ 检索要跑 query embedding + 向量召回 + BM25 重排，是全系统最贵的读；
商品列表带 count + join 两次查询，且是最热接口。

**降级设计（关键）**：Redis 不可用时**熔断 30 秒**，期间缓存操作全部 no-op、直接查源头 ——
请求既不变慢也不报错。**Redis 是纯优化，不是硬依赖**。
`/api/health` 的 `cache` 字段可查 `hits / misses / hit_rate / cooldown_remaining`。

**类型一致性**：`price` 从 psycopg2 出来是 `Decimal`，JSON 装不下。缓存边界用 `_jsonable()`
在**命中与未命中两条路径**上统一转 `float`，避免「同一次调用、有时 Decimal 有时 str」。

### 逐级降级

| 故障 | 行为 |
|------|------|
| `LLM_API_KEY` 未配置 | `run_stream` 直接返回友好提示（**不 500**），`/api/health` 标 `degraded` |
| supervisor LLM 调用异常 | 降级 `DEFAULT_ROUTE=finish`，日志 `supervisor routing failed` |
| 子 Agent 异常 | 兜底话术「查询过程出现异常，请稍后再试」 |
| 单个工具异常 | `TOOL_ERROR_TEMPLATE`，其余工具继续；不影响整轮 |
| ReAct 超 `max_steps` | 确定性兜底话术（不是空回答） |
| Redis 不可用 | 熔断 + 直查 |
| trace 落库失败 | 旁路吞掉，不影响主流程 |
| `resolve_target` 返回非法节点 | `create_selector` 降级 `finish` + warning |

| 鉴权 | JWT（HS256）：正式账号走 `/api/shop/auth/login`（bcrypt 校验 + 含 role）；`/api/token` 是 demo 入口，见下 |
| **demo token 开关** | `/api/token` **无凭证签发任意 user_id 的 JWT**，会绕过全部 IDOR 校验 → 由 `ALLOW_DEMO_TOKEN` 控制：非 production 默认开，`APP_ENV=production` **强制关**；关闭时返回 404（不暴露端点存在）；签发时打 WARNING |
| **默认密钥体检** | 启动时 `_audit_secrets()`：`JWT_SECRET` / `INTERNAL_API_TOKEN` 仍是默认值 → 非生产告警、**production 拒绝启动** |
| 密码 | bcrypt 哈希 |
| **身份解析** | `_resolve_user_id` 只做**精确**匹配（数字 id / email / nickname 全等），**禁止 ILIKE 前缀匹配**（前缀匹配 = 「谁先命中谁就是你」的身份混淆） |
| **IDOR 防护** | `_check_conversation_owner()`：会话必须属于当前登录用户；不存在返回 **404**（而非 403，避免泄露「会话是否存在」），越权返回 403 并记 warning |
| **数据隔离** | 所有业务查询 `WHERE user_id = %s`；工具侧 `user_id` 由服务端注入（§6） |
| **trace 隔离** | `/api/traces` 强制带 `user_id` 过滤 |
| **Prompt 注入** | system prompt 与用户输入**分离为不同 Message**，不再字符串拼接 |
| **越权下单** | `prepare/commit` 各自 `_resolve_uid(state["user_id"])`，不接受请求体里的用户身份 |
| Internal API | `X-Internal-Token` 认证；`hmac.compare_digest` 时序安全比较；production 下仍是默认 token → 503 |
| 管理员接口 | `Depends(require_admin)`（role == "admin"） |
| 超卖 | `SELECT ... FOR UPDATE` 行级锁 + 事务内校验库存 |
| 工具面收敛 | 图里只注册 7 个真绑定工具；无鉴权的「列出全站订单」函数已删除（防止被误注册成越权工具） |
| 慢查询 / 长事务 | 连接池 `statement_timeout` + `idle_in_transaction_session_timeout`，避免连接被长期占用 |

## 12. 可观测性

- **`agent_traces` 表**：每次请求一条 —— `route` / 节点链 / `tool_calls`（含 args、耗时、observation 摘要）/
  `llm_calls` / `prompt_tokens` / `completion_tokens` / `duration_ms` / `status` / `error`；
- **`GET /api/traces`**：返回统计（总数、按状态、按路由、平均耗时）+ 明细（按 user_id 过滤）；
- **LLM 用量计量**：`llm/usage.py` 的 `Usage` + `ContextVar` 跨线程传递；
  流式拿不到 usage（未开 `stream_options.include_usage`，部分兼容端点不支持该参数）→
  按字符数估算并标 `estimated=True`；
- **结构化日志**：`request_id` 贯穿请求；关键节点（supervisor 降级、clarify、order draft/commit、
  react 超步、工具异常）都有明确日志；
- **`/api/health`**：LLM / 向量库 chunk 数 / 缓存统计 / agent 就绪 / checkpointer 类型 / trace 统计。

## 13. 电商后端（shop）

| 服务 | 关键设计 |
|------|----------|
| `user` | 注册（bcrypt）+ 登录（JWT 含 role） |
| `product` | 分类树、列表（分类筛选 + 关键词 + 分页）、详情 |
| `cart` | UPSERT 幂等加购、改数量、删除 |
| `order` | **下单**：`FOR UPDATE` 锁库存 → 校验 → 扣库存 → 建订单 → 快照明细 → 清购物车（单事务）；**支付**：幂等（`FOR UPDATE` + 状态校验 + 自动生成物流）；**取消**：回滚库存；**超时扫描**：`cancel_expired` 由后台任务周期执行 |
| `logistics` | 按 order_id + user_id 查轨迹 |
| `after_sale` | 申请 / 查询（订单号或工单号） |

**下单事务**：

```
BEGIN
  SELECT ... FROM shop.products WHERE id IN (...) FOR UPDATE  ← 行级锁防超卖
  逐条校验 stock >= quantity                                  ← 不足 → ROLLBACK
  UPDATE shop.products SET stock = stock - quantity
  INSERT INTO shop.orders (status='pending', recipient, ...)  ← recipient 一并落库
  INSERT INTO shop.order_items (快照：product_name / price)
  DELETE FROM shop.cart_items
COMMIT
```

`OrderService.create_direct()` 是「Agent 直下单」与「C 端下单」的**同一入口**，保证两条路径行为一致。

## 16. 运行、测试与部署

### 本地运行

```bash
# 1) 起 Postgres + Redis
docker-compose up -d

# 2) 导入建表与种子（首次创建数据卷时 compose 已自动挂载；手动导入亦可）
docker exec -i qa_agent_pgsql psql -U user -d agent < init.sql

# 3) 配置 .env（至少 LLM_API_KEY）

# 4) 装依赖并启动
pip.bat install -r requirements.txt
python main.py            # 或 run.bat
# → http://localhost:8000
```

### 测试（四层）

```bash
# ① 离线单元/集成（127 项，进程内异步，不花钱）
python tests/test_agent_offline.py

# ② 多轮剧本回放（24 项）
python scripts/scenario_test.py

# ③ 端到端（54 项）—— 需两个终端
python scripts/mock_llm_server.py                    # 终端 A：Mock LLM :8099
LLM_API_KEY=mock LLM_BASE_URL=http://127.0.0.1:8099/v1 LLM_MODEL=mock-model \
  python -m uvicorn main:app --port 8131             # 终端 B：应用
python scripts/e2e_mock.py                           # 终端 C：跑验证

# ④ 路由评测（需真实 LLM_API_KEY）
python scripts/eval_routing.py

# 附：PostgreSQL 冒烟
python scripts/smoke_test.py
```

**四层各管什么**（这是本项目测试策略的核心）：

| 层 | 能验证 | 验证不了 |
|----|--------|----------|
| 离线单元 | 图结构、节点逻辑、状态机、并发、trace、鉴权开关、工具超时 | 自研适配器 × 框架契约、SSE 与前端契约 |
| 剧本回放 | 跨轮状态机、多轮人机对话 | 真实 HTTP / 流式适配器 |
| 端到端 | HTTP → 图 → 工具 → SSE token → traces、IDOR、内部接口鉴权 | — |
| 路由评测 | 真实 LLM 下的路由/抽槽准确率 | — |

> 只有端到端层能抓到「`_generate` 缺 `run_manager`」、「`user_id` 未注入」
> 和「async 校验函数漏写 `await` 导致静默失效」这几类真 bug ——
> 所以这一层不是「锦上添花」，是必需品。
>
> 另有一个**非测试**的验证手段：`_scratch/probe_loop_block.py`，
> 用 A/B 对照实证「同步调用是否真的移出了事件循环」（见 §9 证据）。

### 容器化

```bash
docker compose --profile app up -d --build     # 整栈（postgres + redis + app）
```

`app` 服务默认不启动（`profiles: ["app"]`），避免与本地 `python main.py` 抢 8000 端口。
容器内用服务名互访（`postgres:5432` / `redis:6379`），并复用宿主机的 `chroma_db`。

## 17. 已知边界与后续方向

| 项 | 现状 | 建议 |
|----|------|------|
| 订单超时扫描 | 单进程 `asyncio` 任务 | 多副本部署时换外部分布式调度（避免多实例重复扫描） |
| 会话锁 | 进程内 `asyncio.Lock` + `KeyedLocks` | 多副本部署时换 DB 行锁 / Redis 分布式锁 |
| 图持久化 | 本地 SQLite | 大流量/多实例换 AsyncPostgresSaver |
| 限流 | 无 | 网关层按 user_id / IP 限流（防单账号刷爆工具层） |
| 缓存一致性 | Cache-Aside 存在短失效窗口 | 关键读路径可改 write-through 或加版本号 |
| 连接池 | `maxconn=10`（故意小于线程池上限） | 高并发部署按 `SHOP_DB_POOL_MAX` 上调，并同步调 `TOOL_TIMEOUT_SEC` |
| 流式 token 计量 | 按字符数估算（标 `estimated`） | 上游支持 `stream_options.include_usage` 后改用真实 usage |
| 支付 | 模拟支付 | 接真实支付渠道时补对账与回调幂等 |
| 路由 | 单跳 | 若出现一轮多意图，可扩展为受限多跳（需防路由震荡） |
| 前端 | 单文件原生 JS | 需要工程化时迁移到 Vite + 组件框架 |

> 安全上线检查清单（三条，缺一不可）：
> 1. `APP_ENV=production`（自动关闭 `/api/token`、默认密钥拒绝启动）；
> 2. `JWT_SECRET` / `INTERNAL_API_TOKEN` 换成随机长串；
> 3. `LLM_API_KEY` 配置真实密钥（否则全程降级话术）。
