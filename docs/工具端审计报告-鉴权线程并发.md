## 2. 鉴权维度的发现

### A1 🔴 致命：`/api/token` 无凭证签发任意身份（已修）

```python
@router.post("/token")
def generate_token(req: TokenRequest):
    token = create_access_token(req.user_id)   # user_id 完全由请求方指定
```

`POST /api/token {"user_id": "2"}` → 直接拿到一条**合法的**、可冒充用户 2 的 JWT。
而 AI 客服全部接口（`/api/chat`、`/api/chat/stream`、`/api/conversations`、`/api/traces`）
都通过 `get_current_user` 接受该 token。

**为什么这比普通越权更严重**：攻击者不是「越权访问他人会话」，而是「**变成受害者本人**」。
因此 `_assert_conversation_owner`（防 IDOR）这条防线**完全绕过** —— 它校验的是
「该会话是否属于你」，而攻击者手里拿的已经是受害者的身份。攻击者可以：
拿走某人全部订单、物流、售后、购物车，并以其名义下单。

**修法**（`apps/customer_service/routes.py`）：

```python
APP_ENV = (os.getenv("APP_ENV") or "development").strip().lower()
ALLOW_DEMO_TOKEN = _env_bool("ALLOW_DEMO_TOKEN", APP_ENV != "production")
```

- 默认策略：**非 production 开启**（保证 `python main.py` 开箱即用），**production 强制关闭**；
- 关闭时返回 **404 而非 403**，不对外暴露该端点存在；
- 签发时打 `WARNING` 级日志；
- 启动时（`main.py: lifespan`）额外提示「⚠️ /api/token 已启用」。

### A2 🟠 身份解析做前缀匹配 = 身份混淆（已修）

```python
row = query_one(
    "SELECT id FROM shop.users WHERE nickname = %s OR email ILIKE %s",
    (user_id, f"{user_id}%"),        # ← 前缀匹配
)
```

`ILIKE '<user_id>%'` 的语义是「**谁先命中谁就是你**」。
JWT 里 `sub` 是字符串时走这条路，于是 `sub="a"` 会匹配到任意以 `a` 开头的邮箱
（`alice@…`），取决于数据库返回的第一行 —— 这是典型的 privilege confusion。

**修法**：改为**精确相等**匹配，并在函数里写明「勿改回模糊匹配」的安全约定：

```python
"SELECT id FROM shop.users WHERE email = %s OR nickname = %s"
```

### A3 🟠 默认密钥硬编码（已加启动体检）

| 变量 | 默认值 | 后果 |
|------|--------|------|
| `JWT_SECRET` | `demo-secret-change-in-production` | 可自行伪造任意 JWT |
| `INTERNAL_API_TOKEN` | `dev-internal-token` | `/internal/*` 泄露**全量**订单与用户信息 |

**修法**：`main.py` 新增 `_audit_secrets()`，在 lifespan 最早期执行 ——
非生产只告警（不破坏 demo），**production 直接抛异常拒绝启动**。
`/internal` 侧另加一层兜底（见 A4）。

### A4 🟡 内部接口用 `!=` 比较令牌（已修）

`!=` 按首个不同字节提前返回，理论上可逐字节爆破；且生产若忘配 token 就直接裸奔。

**修法**（`apps/shop/internal/routes.py`）：

```python
if INTERNAL_TOKEN == _DEFAULT_INTERNAL_TOKEN and APP_ENV == "production":
    raise HTTPException(503, "internal API token not configured")
if not hmac.compare_digest(x_internal_token, INTERNAL_TOKEN):
    raise HTTPException(401, "Invalid internal token")
```

### A5 🟡 `list_all_orders` 是「一句话导出全站订单」的隐患工具（已删）

`tools/order_search.py` 里存在一个**无 user 过滤、无鉴权**的「列出全站订单」函数，
并且被 `tools/__init__.py` re-export。它目前没被注册成 Agent 工具，但导出面本身就是风险 ——
将来任何人把它加进 `main.py` 的工具列表，就等于给 Agent 开了一个「导出全站订单」的能力。

**修法**：删除该函数与导出，并在 `tools/__init__.py` 写清原因；
真正的管理员列表在 `apps/shop/b_endpoint/admin.py`，带 `Depends(require_admin)`。

### A6 ✅ 鉴权维度做对的地方（保留）

- **鉴权主体由服务端注入**：`react._inject_context()` 只注入工具**自己声明**的参数名，
  且**服务端值覆盖 LLM 值** —— LLM 无法伪造越权身份，也不会污染不需要 `user_id` 的工具。
- **IDOR 校验**：不存在返回 404 而非 403，避免泄露「会话是否存在」。
- **admin 接口**独立 `require_admin`；**内部接口**独立 token；密码用 **bcrypt**。
- demo token 只签发 `sub`（无 `role`），够不到 admin 接口。

## 3. 线程维度的发现

### T1 🟠 系统性缺陷：同步 DB 调用阻塞事件循环（已修）

工具调用**早就**正确地走了 `asyncio.to_thread`，但**会话管理**这条路径漏了：

| 调用点 | 位置 | 性质 |
|--------|------|------|
| `get_owner()` | `routes._assert_conversation_owner`（async 路由内直接调用） | 同步 SQLAlchemy 查询 |
| `get_context()` / `add_message()` | `MasterAgent._prepare` | 每次请求 2 次同步 PG 往返 |
| `add_message()` | 请求收尾落助手消息 | 同步 PG |
| `add_message()` | `_fallback_response` | 同步 PG |
| `create()` | `_ensure_conversation` | 同步 PG |
| `TraceRecorder.save()` | 每次请求落 trace | 同步 PG |

**后果**：单进程下，这些往返期间**整个事件循环停摆** —— 不只是当前会话，
**所有并发请求、所有 SSE 连接一起卡住**。这正是「能跑通、但一上并发就整体变慢」的根因类型。

**修法**：把上述调用统一改为 `await asyncio.to_thread(...)`：

- `MasterAgent._ensure_conversation` / `_fallback_response` 改为 `async`；
- `_prepare`、`arun`、`run_stream` 的所有会话管理与 trace 落库均走线程池；
- `routes` 拆成 `_check_conversation_owner`（同步，供线程池内的同步路由用）
  与 `_assert_conversation_owner`（async 包装，供 async 路由用）。

> ⚠️ 修复过程中发现一个「静默失效」陷阱：`get_conversation` 是**同步**路由，
> 一度被误写成调用 async 版 `_assert_conversation_owner(...)` 而**没有 await** ——
> 协程被创建但从未执行，**越权校验静默失效、接口返回 200**。
> 端到端场景 6 抓住了它。教训：把 `def` 路由改成调用 async 函数时，
> 没有 await 不会报错，只会「什么都不做」。

**A/B 实证**（`_scratch/probe_loop_block.py`，给会话管理器注入 0.3s 同步睡眠模拟 DB 往返）：

```
A) 现状：走 to_thread   总耗时=1.56s  ticks= 52  max_loop_lag=  14.9 ms
B) 对照：直接阻塞循环   总耗时=1.50s  ticks=  1  max_loop_lag= 428.3 ms
```

同样 1.5 秒的请求、同样含 0.9s 人为阻塞：修复后事件循环仍调度了 **52 次** tick、
最大滞后 **14.9ms**；改成直接调用后 tick 掉到 **1 次**、滞后 **428ms**。
差距约 28 倍，结论明确。

### T2 🟠 工具调用无超时（已修）

`await asyncio.to_thread(tool.run, args)` 没有超时。工具是同步函数、跑在默认线程池
（上限 `min(32, cpu+4)`），若某次 DB 查询卡住（行锁等待 / 连接半死），
**该工作线程会被永久占用**，几次之后工具层整体饿死。

**修法**（`react._call_tool`）：

```python
TOOL_TIMEOUT_SEC = float(os.getenv("TOOL_TIMEOUT_SEC", "8"))
obs = await asyncio.wait_for(
    asyncio.to_thread(tool.run, call_args), timeout=TOOL_TIMEOUT_SEC)
```

诚实说明其边界（已写进 docstring）：`to_thread` 的线程**无法被真正取消**，
`wait_for` 到期只是让调用方快速失败、不再堆积请求；被卡住的线程随查询自身结束而回收。
因此必须与 T3 的 `statement_timeout` **双保险**：应用侧快速失败 + 数据库侧真正掐断查询。

### T3 🟠 数据库无 statement timeout（已修）

`ThreadedConnectionPool` 的 `options` 只设了 `search_path`。没有 `statement_timeout`，
慢查询或「忘记提交」的事务会长期占用连接（池上限仅 10）。

**修法**（`infrastructure/shop_database.py`）：

```python
CONN_OPTIONS = (
    "-c search_path=shop,public"
    f" -c statement_timeout={...默认 5000ms}"
    f" -c idle_in_transaction_session_timeout={...默认 30000ms}"
)
```

### T4 🟡 连接池上限与线程池上限不匹配（已改为可配）

池 `maxconn=10` 小于线程池上限（最多 32）。这是**故意的背压**（让池耗尽成为信号
而不是把数据库打爆），但之前不可调。现已支持 `SHOP_DB_POOL_MIN/MAX` 按部署调整，
并在代码里写明「故意小于线程池上限」的设计意图。

### T5 ✅ 线程维度做对的地方（保留）

- `_get_pool()` **双检加锁**，并发首调只创建一个池；
- `get_conn()` 以 contextmanager 保证 `putconn` / `rollback`，异常不泄露连接；
- 池耗尽 / DB down 被转成可读 `RuntimeError`，工具层降级而非 500；
- 缓存**懒连接 + 熔断**，Redis 挂了只降命中率（计数器非原子，但已声明为 advisory）。

## 4. 并发维度的发现

### C1 🟠 购物车结算未锁 cart 行 → 重复建单（已修）

`OrderService.create()` 锁了 `products`（防超卖），但**没有锁 `cart_items`**：

```
T1: SELECT cart_items ...          → 读到 [商品A ×1]
T2: SELECT cart_items ...          → 读到 [商品A ×1]   （同一批）
T1: 扣库存 + 建单 + DELETE cart
T2: 扣库存 + 建单 + DELETE cart     ← 重复建单、库存扣两次
```

购物车够用时（库存充足），两次都会成功 → **用户一份购物车出两张订单**。

**修法**：先锁购物车行，再走原有流程：

```sql
SELECT ci.product_id, ci.quantity, p.name, p.price, p.stock
FROM shop.cart_items ci JOIN shop.products p ON p.id = ci.product_id
WHERE ci.user_id = %s
ORDER BY ci.product_id
FOR UPDATE OF ci          -- ← 新增：锁购物车行
```

后到的请求阻塞，待前者提交（已 `DELETE cart_items`）后读到空集 →
得到「购物车为空」，**不会重复建单**。

**负向对照实证**（把 `FOR UPDATE OF ci` 去掉后跑 T18）：

```
去掉行锁：[FAIL] 恰好一单成功（无重复建单）   [('ok', 1067), ('ok', 1068)]
          [FAIL] 库存只扣减一次   97 → 95
加回行锁：81/81 通过
```

### C2 ✅ 库存防超卖（本来就对）

`create_direct` / `create` 都是 `SELECT ... FOR UPDATE` + `UPDATE ... WHERE stock >= qty`
双保险；`pay` / `cancel` 有 `FOR UPDATE` + 状态检查保证幂等。
`sweep` 逐单独立事务、捕获 `ValueError` 跳过状态已变者，不长时间持锁。

### C3 ✅ 会话级串行化（本来就对）

三层锁分工正确，且各自边界都写明了：

| 锁 | 作用域 | 解决的问题 |
|----|--------|------------|
| `MasterAgent._locks`（asyncio.Lock，按 conversation_id） | 单进程 | 同一会话并发写 checkpoint 互相覆盖 |
| `ConversationManager._locks`（KeyedLocks，threading.Lock） | 单进程 | `SELECT max(turn_number)` 与 `INSERT` 之间的竞态 |
| PostgreSQL 行锁（`FOR UPDATE`） | 跨进程 | 库存、购物车、订单状态 |

会话锁覆盖「落用户消息 → 跑图 → 落助手消息」全过程，
保证 user/assistant 两条消息成对写入、`turn_number` 不错配。

### C4 🟡 Cache-Aside 的失效窗口（已知、可接受）

写路径 `cache.invalidate(NS_SHOP)` 之后仍可能有并发读把旧值回填（库存在途）。
这是 Cache-Aside 的标准现象；正确性由 DB 行锁保证，缓存只影响**短窗口内的展示**。
不修，但已明确记录。

### C5 🟡 单进程锁的边界（已知、属规模化）

所有进程内锁（asyncio.Lock / threading.Lock）多副本部署即失效；
`OrderService.cancel_expired` 由每个副本各跑一份（幂等，仅浪费）。
属**规模化议题，不是缺陷**，已在文档「已知边界」列出。

## 7. 剩余边界（**未修，属规模化议题，非缺陷**）

| 项 | 现状 | 规模化时的做法 |
|----|------|----------------|
| 进程内锁 | `asyncio.Lock` + `threading.Lock` 仅单进程有效 | 换成 DB 行锁（`SELECT … FOR UPDATE`）或 Redis 分布式锁 |
