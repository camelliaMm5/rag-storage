# 重构改动说明

> 本轮把项目从「一个能跑的 LangGraph Demo」改造成「一个结构完整的多智能体 Agent 工程」。
> 本文按 **问题 → 根因 → 改法 → 证据** 组织，方便逐条回溯。

---

## 0. 结论速览

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 路由 | 单个大 prompt 让 LLM 直接输出回复 | Supervisor 只做「分类 + 抽槽」，纯函数 `resolve_target` 决定图走向 |
| 子 Agent | 「一次性带工具调用」的伪 ReAct | 受限 ReAct 循环（`react.py`），带工具轨迹与步数上限 |
| 多轮 | 靠 LLM 复述上下文，缺参就断 | 澄清闭环：`pending_intent` 跨轮记忆 + 正则兜底补参 |
| 下单 | 一次 LLM 调用直接落库 | 两阶段（prepare 只读回显 → commit 单事务），human-in-the-loop |
| 记忆 | Checkpointer + PG 双写但同步/异步链路冲突 | 统一异步单链路（`AsyncSqliteSaver`），checkpoint 热记忆 + PG 耐久记忆 |
| 并发 | 同会话并发会丢消息、turn_number 重复 | per-conversation 锁 + `KeyedLocks` |
| 流式 | SSE 只推节点进度，无 token | `astream(stream_mode=["updates","messages","custom"])`，token 级打字机 |
| 可观测性 | 只有 print 日志 | `agent_traces` 表 + `/api/traces` + LLM 用量计量 |
| 评测 | 无 | 离线 67 项 + 场景剧本 24 项 + 端到端 28 项 + 路由评测集 16 条 |
| 死代码 | `agent.py` / `graph.py` / `order_repository.py` / `domain/order/` 并存 | 全部删除 |

**验证结果**：离线 `67/67` · 场景 `24/24` · 端到端 `28/28`（真实 HTTP + Mock LLM）。

## 1. P1-a 路由内核与子 Agent 真 ReAct 化

### 问题 1.1 —— 路由没有「内核」，只有一段 prompt

**旧实现**：一个 system prompt 里塞进「路由 + 抽槽 + 回答」三件事，LLM 直接吐最终文本。
症状：

- 路由错了没有任何兜底，图走向靠 LLM 自由发挥；
- 图节点名硬编码，`route` 一旦出现未预期值就是 `KeyError`；
- 抽槽结果散落在自然语言里，下一轮拿不到。

**改法** —— 新增 `domain/customer_service/routing.py`，把「决策」提炼成**纯函数**：

```
路由白名单 ROUTE_WHITELIST     非法 route → DEFAULT_ROUTE("finish")
normalize_route()              别名归一：order_status → order、express → logistics …
Slot / missing_slots()         槽位规格与缺失判定（order_id / ticket_id / product / address）
clarify_question()             缺参时生成确定性反问（不靠 LLM）
merge_slots()                  跨轮槽位合并
extract_order_id()             正则兜底抽单号
is_affirmative / is_negative   肯定/否定判定（否定优先）
resolve_target()               纯函数：由 (route, slots, pending) 决定图走向
```

**收益**：路由决策完全可单测（T2 段纯函数测试）、图走向永不 `KeyError`（`create_selector` 会把非法目标降级到 `finish` 并打 warning）。

### 问题 1.2 —— 子 Agent 不是 ReAct，是「一次带工具的调用」

**旧实现**：调一次 LLM，如果带 `tool_calls` 就执行、然后把工具结果拼进 prompt 再调一次；
没有步数上限、没有工具轨迹、异常直接冒泡。

**改法** —— 新增 `domain/customer_service/react.py`：

```python
run_react(llm, tools_by_name, system_prompt, messages, max_steps, window, user_context)
  → ReactOutcome(content, steps: list[ToolStep], llm_calls)
```

- 受限循环：`max_steps` 上限，超限返回确定性兜底话术（不是空回答）；
- `ToolStep` 记录 `name/args/observation/duration_ms`，直接落 trace；
- 工具在**子线程**执行（`asyncio.to_thread`），DB I/O 不阻塞事件循环；
- 工具异常被兜住（`TOOL_ERROR_TEMPLATE`），不让一个工具炸掉整轮对话；
- 关键点：用 `llm.astream` 而非 `ainvoke` —— 外层 `messages` 模式要靠它拿 token 增量。

### 问题 1.3 —— prompt 注入风险

**旧实现**：把 `user_input` 拼进 system prompt 模板。

**改法**：`prompts.py` 中 `SUPERVISOR_SYSTEM_PROMPT` 等改为**独立 SystemMessage**，用户输入走 `HumanMessage`，两者不再字符串拼接。用户输入无法再「越狱」改写 system 指令。

## 2. P1-b 澄清闭环与下单两阶段

### 问题 2.1 —— 缺参即断

**旧实现**：用户说「帮我查订单」→ LLM 判 order 路由 → 没有订单号 → 工具报错或空回答。

**改法** —— 澄清闭环：

```
supervisor 抽槽 → missing_slots() 非空 → clarify 节点
    ├── 生成反问（确定性话术）           "请提供订单号，例如 1001"
    └── pending_intent = {route, order_action, slots, missing}  ← 存进 state
下一轮 "1001"
    ├── supervisor 恢复 pending → route 覆盖回 order/logistics
    └── extract_order_id() 正则兜底补上 order_id  ← 必须在「续跑」之后，按最终 route 判断
```

**踩坑**：正则补参最初放在 pending 恢复**之前**，而用户只回 `"1001"` 时 LLM 判成 `finish`，
走不到补参那一步 → 回归测试 T6 直接红。修正为「先续跑、再按最终 route 补参」。

### 问题 2.2 —— 下单没有确认环节

**旧实现**：一句「我要买 X1」直接调 `place_order` 落库 —— 地址、数量、收件人都可能错，
且用户没有任何反悔机会。

**改法** —— 两阶段下单（`create_place_order_nodes` → prepare / commit / cancel）：

```
prepare : 只读校验商品与库存 + 生成草稿回显（**不写库**）
          下单成功请确认：X1 智能门锁 ×1 / ¥1599.00 / 收货地址：…
commit  : 用户明确肯定 → OrderService.create_direct() 单事务落库
cancel  : 用户否定 → 丢弃草稿
```

配套修复：

- `is_affirmative("不要")` 曾误判为 `True` —— 改为**否定优先**（先排除否定词再匹配肯定词），并加回归测试 T5；
- `place_order` 走 `create_direct` **单事务**（扣库存 + 建订单 + 快照明细 + 清购物车同一事务），
  并补上 `recipient` 落库（旧版直接丢弃收件人）。

## 3. P1-c 并发与竞态

### 问题 3.1 —— 同会话并发丢消息

**旧实现**：`add_message` 里 `SELECT max(turn_number)` 再 `INSERT`，两步之间无锁。
5 个并发请求 → 多条消息拿到同一个 `turn_number`，甚至互相覆盖。

**改法**：

1. `utils/conversation.py` 新增 `KeyedLocks`（按 key 互斥），`turn_number` 计算放进锁内；
2. `MasterAgent` 增加 per-conversation `asyncio.Lock`，锁范围**覆盖「用户消息 + 助手消息」成对写入**
   —— 只锁单条 INSERT 是不够的，成对写入才能保证问答不错配。

**证据**：T11 并发段 —— 5 并发请求 → 消息总数恰为 10，`user.turn_number` 唯一且为 `1..5`。

### 问题 3.2 —— checkpointer 同步/异步双链路冲突

**旧实现**：同步 `SqliteSaver` + 异步 `AsyncSqliteSaver` 并存。同步链路一用 `astream` 就
`NotImplementedError: The SqliteSaver does not support async methods`。

**根因**：`AsyncSqliteSaver.__init__` 内部调用 `asyncio.get_running_loop()`，只能在**运行中的事件循环**里构造；
在 import 期构造会抛 `RuntimeError`，若被 `except` 吞掉就静默退化成内存态 —— 这正是旧版
`checkpoints.db` 有表结构但 **0 行数据**的原因（持久化从未生效）。

**改法**：`checkpointer.py` 只保留异步单链路，删除 `sync_checkpointer`；所有节点统一 `async def`。

## 4. P2 Token 级流式（打字机）

### 问题 4.1 —— 流式只有进度，没有字

**旧实现**：`SSE` 推的是节点进度事件，正文靠最后一次性返回。

**改法**（三层打通）：

1. `llm/client.py` 新增 `stream_raw()` —— 真流式，逐 delta 产出
   `{"content", "tool_calls":[{index, id, name, arguments}]}`，
   **tool_calls 的 `arguments` 是片段**，必须按 index 拼接（否则带工具的流式响应会丢 tool_calls，
   ReAct 循环误判「不需要工具」直接返回空回答）；
2. `llm/langchain_model.py` —— `_stream()` 逐 delta yield `ChatGenerationChunk(AIMessageChunk)`；
3. `langgraph_agent.py` —— `graph.astream(stream_mode=["updates","messages","custom"])`：
   - `messages` → token 增量（打字机）
   - `custom` → 工具调用进度（`get_stream_writer`）
   - `updates` → 节点级事件 + 路由结果

前端 `static/index.html` 改为 `ensureStreamBubble / appendToken` 逐字渲染，并与 `agent_result` 去重。

### 问题 4.2 —— 端到端暴露的两个真 bug（离线测试测不出来）

这两个 bug 是**只有真实调用链才会暴露**的，价值最高：

**（1）`_generate()` 缺 `run_manager` 形参 → 全量降级**

```
TypeError: LangChainChatModel._generate() takes from 2 to 3 positional arguments but 4 were given
```

- **根因**：langchain-core 的 `_agenerate` 默认实现把 `run_manager` **作为位置参数**传给 `_generate`。
  离线 `ScriptedChatModel` 自己声明了该参数，所以离线测试全绿；接上 Mock LLM 走真实
  `ainvoke` 立刻炸。
- **症状**：`supervisor routing failed, falling back to finish` —— 所有请求都降级成闲聊，
  `/api/traces` 里 `by_route` 清一色 `finish`。
- **改法**：`_generate(self, messages, stop=None, run_manager=None, **kwargs)`，并在 docstring 里
  写清「为什么必须显式声明」。
- **防回归**：新增 `tests/fake_openai.py` + 测试 T16，把适配器契约固定下来。

**（2）`user_id` 没有注入工具 → 所有业务查询变「请先登录」**

- **根因**：ReAct 循环只把 LLM 给的 `args` 透传给工具（`tool.run(args)`），
  而 `state["user_id"]` 从未注入。于是 `query_order / query_logistics / query_after_sale /
  query_cart / list_my_orders` 一律返回「请先登录后再查询」。
  下单能用，是因为 `prepare/commit` 节点自己解析了 uid，绕过了工具层 —— 所以离线测试没发现。
- **改法**：`react.py` 新增 `_inject_context()`：

  ```python
  declared = {p.name for p in tool.parameters if p.name in context}
  return {**args, **{k: context[k] for k in declared}}
  ```

  **只注入工具自己声明的参数名**，且**以服务端值为准覆盖 LLM 同名参数**——
  这样鉴权主体永远来自 JWT，LLM 无法伪造越权身份；同时不会把 `user_id` 硬塞给
  `search_faq` 这类不需要它的工具。
- **防回归**：测试 T14（LLM 不传 user_id 时仍由服务端注入）、端到端场景 1。

**（3）流式事件重影（token 2 倍）**

- **根因**：`stream_mode="messages"` 会**既**吐流式增量（`AIMessageChunk`），
  **又**吐节点 `return` 的整条消息（`AIMessage`）。前端于是收到 176 个单字 + 1 条 176 字的完整消息。
- **定位方法**：抓原始 SSE 事件分布 —— `sizes = [1,1,...,1, 176]`，一眼看出「逐字 + 整条」。
  再用图探针确认类型差异：`AIMessageChunk`（增量） vs `AIMessage`（整条）。
- **改法**：`run_stream` 只转发 `isinstance(chunk, AIMessageChunk)`。
- **防回归**：T15（token 事件数 == 回答字符数），并给 `ScriptedChatModel` 补上真
  `_stream`，让离线测试也走真实 token 路径（否则过滤后一个 token 都没有）。

**（4）`routing` 事件重复**

- **根因**：`supervisor` 的**进度事件名**也叫 `routing`，而语义化的 routing 事件
  （带 `route/extract`）另有一条 → 前端收到两条 routing，其中一条没有 `route` 字段
  （会显示「已路由到: undefined」）。
- **改法**：进度事件名改为 `supervisor`，前端补 `case 'supervisor'`。

**修复后事件序列**（干净且语义明确）：

```
supervisor(executing) → routing(routed, route=logistics) → tool(start) → tool(done)
   → logistics_agent(executing) → …token 增量… → done(route=logistics)
```

## 6. 经验教训（Lessons Learned）

1. **离线测试会造假绿**。脚本模型自己声明了 `run_manager`，于是「契约漂移」被完美掩盖。
   凡是「自研适配器 × 框架隐式契约」的地方，都必须有一条走真实调用链的测试。
2. **「能用」的功能最容易被漏测**。下单能用（节点自己解析 uid），掩盖了工具层全员「请先登录」。
   端到端场景要覆盖**每一条**业务链路，而不是抽查一条。
3. **框架的方便功能有暗坑**。`stream_mode="messages"` 同时吐增量和整条消息，
   不看一眼原始事件就不会发现重影。遇到「数据翻倍」，先怀疑双份来源，用分布（长度直方图）定位。
4. **纯函数是复杂状态机的救星**。把路由/槽位/走向提炼成纯函数后，
   澄清闭环、否定优先这些边界条件都能一条断言覆盖，而不需要跑整张图。
5. **鉴权主体必须服务端注入**。凡是「身份」类参数，绝不能听 LLM 的；只注入工具声明的参数名，
   既安全又不会污染无关工具。

## 7. 第二轮：工具端审计（鉴权 / 线程 / 并发）

> 完整报告见 **[工具端审计报告-鉴权线程并发.md](工具端审计报告-鉴权线程并发.md)**。
> 本节只记「问题 → 根因 → 改法 → 证据」。

### 7.1 鉴权

| 问题 | 根因 | 改法 |
|------|------|------|
| 🔴 `/api/token` 无凭证签发任意身份 | `create_access_token(req.user_id)` 完全信任请求体 | 加 `ALLOW_DEMO_TOKEN` 开关：非 production 默认开、**production 强制关**；关闭返回 404；签发打 WARNING；启动提示 |
| 🟠 身份解析做前缀匹配 | `email ILIKE '<user_id>%'` = 「谁先命中谁就是你」 | 改**精确**匹配（数字 id / email / nickname 全等） |
| 🟠 默认密钥硬编码 | `JWT_SECRET` / `INTERNAL_API_TOKEN` 都有内置默认值 | 启动期 `_audit_secrets()`：非生产告警、**production 拒绝启动** |
| 🟡 内部接口用 `!=` 比较 | 非时序安全，可逐字节爆破 | `hmac.compare_digest` + production 下默认 token → 503 |
| 🟡 无鉴权的「列出全站订单」函数被 re-export | 一旦被误注册成 Agent 工具就是越权工具 | 删除函数与导出，管理员列表留在带 `require_admin` 的 admin 路由 |

**关键认识**：`/api/token` 这个洞让**所有 IDOR 防护形同虚设** ——
攻击者不是「越权访问他人会话」，而是「变成受害者本人」，
`_assert_conversation_owner` 校验「会话是否属于你」时，你手里的身份已经是受害者的了。

### 7.2 线程

| 问题 | 根因 | 改法 |
|------|------|------|
| 🟠 同步 PG 调用阻塞事件循环 | 工具调用早已走 `to_thread`，但**会话管理这条路径漏了**：`get_owner` / `get_context` / `add_message` / `create` / `tracer.save` 全在事件循环里直接跑 | 统一 `await asyncio.to_thread(...)`；`_ensure_conversation` / `_fallback_response` 转 async；routes 拆同步 `_check_conversation_owner` + async `_assert_conversation_owner` |
| 🟠 工具调用无超时 | `to_thread` 卡住的线程永久占用，几次后工具层饿死 | `asyncio.wait_for(..., TOOL_TIMEOUT_SEC)`（默认 8s）+ 可读降级文案 |
| 🟠 DB 无 statement timeout | 慢查询 / 长事务长期占用连接（池上限仅 10） | 连接池加 `statement_timeout` + `idle_in_transaction_session_timeout` |
| 🟡 池上限不可调 | `maxconn=10` 硬编码 | 改 `SHOP_DB_POOL_MIN/MAX`，并注明「故意小于线程池上限」的设计意图 |

**A/B 实证**（`_scratch/probe_loop_block.py`，注入 0.3s 同步睡眠模拟 DB 往返）：

```
A) 现状：走 to_thread   总耗时=1.56s  ticks= 52  max_loop_lag=  14.9 ms
B) 对照：直接阻塞循环   总耗时=1.50s  ticks=  1  max_loop_lag= 428.3 ms
```

**顺带抓到一个静默失效**：`get_conversation`（同步路由）一度被改成调用 async 版
`_assert_conversation_owner(...)` 而**没写 `await`** —— 协程被创建但从不执行，
越权校验**静默失效、返回 200**。端到端场景 6 抓到。教训：**把 `def` 路由改成调 async 函数，
忘写 `await` 不会报错，只会什么都不做**。

### 7.5 经验教训（第二轮追加）

6. **「能跑通」不等于「不阻塞」**。功能正确性和调度正确性是两回事：
   一个接口可以返回完全正确的结果，同时把整个事件循环卡死 428ms。
   这类问题只能靠**度量**（loop lag / tick 数）而不是靠断言发现。
7. **安全开关要「默认安全 + 可开可关」**。demo 入口不能直接删（会破坏开箱体验），
   也不能默认开（会带上线）。用「非生产默认开 / 生产强制关 + 启动体检」同时满足两边。
8. **修 bug 时先写「能抓到它的测试」，再修**。本轮 3 个缺陷都是先写探针/负向对照确认能复现，
   才动手改 —— 否则无法证明修复有效。负向对照（把修复回退，确认测试变红）是性价比最高的一步。
9. **同一文件不要并行编辑**。本轮多次出现「并行 Edit 同一文件 → 其中一处静默丢失」，
   最严重的一次就是`_assert_conversation_owner` 漏改导致越权校验失效。
   改同一文件的多处时，老老实实串行。
